# ADR-002: 테스트 설계자·구현자·검증자 실행 주체 분리

- 날짜: 2026-09-08
- 상태: 채택

## 맥락

기존 하네스는 구현자와 실행 검증자를 구분했지만 테스트 시나리오는 Orchestrator가 Skill로 직접
작성했다. 이후 Designer와 Reviewer 식별자는 남겼지만 Builder 식별자를 구현 산출물에 기록하지
않아, Builder가 다른 역할과 같은 컨텍스트여도 독립 검증이 PASS할 수 있는 공백이 남았다.

## 결정

`spring-test-case-designer`를 별도 Agent로 추가한다. Test Designer는 원 요청과 운영 코드에서
시나리오·assertion을 설계하고 `artifacts/02-test-cases.md`만 작성한다. Quality Reviewer는
Designer·Builder와 다른 새 실행 컨텍스트에서 원 요청과 운영 코드로 요구사항을 먼저 재도출한 뒤
테스트 목록, 구현과 실행 결과를 검증한다.

Designer는 `artifacts/02-test-cases.md`에 자신의 식별자만 기록하며 미래 Builder 식별자를 예측하지
않는다. Builder는 `artifacts/03-implementation.md`에 자신의 식별자를 기록하며 미래 Reviewer
식별자를 예측하지 않는다. Reviewer는 `artifacts/04-verification.md`에 자신의 식별자와 세 산출물의
식별자 비교 결과를 기록한다. 세 식별자가 모두 존재하고 쌍별로 서로 달라야 한다. 하나라도 없거나
어느 두 식별자라도 같으면 테스트가 통과해도 FAIL이다.

세 역할은 각각 `fork_turns="none"` 또는 플랫폼의 동등한 무상속 방식으로 만든 별도 세션에서
시작한다. 역할 간 채팅 기록, 대화 요약, 메모리와 내부 추론은 전달하지 않으며 원 요청, 허용된
프로젝트 파일과 직전 단계의 지정 산출물만 handoff한다. 각 산출물에 자기 세션 격리 방식과 허용된
입력을 기록하고 Reviewer가 세 기록을 확인한다. 세션 격리 증거가 없거나 역할 간 컨텍스트 상속이
확인되면 식별자가 달라도 FAIL이다.

## 버린 대안과 이유

- Orchestrator 체크리스트만 추가: 파일 수와 실행 비용은 적지만 실제 실행 주체 분리를 증명하지
  못해 자기검증 편향을 해결하지 못한다.
- 의미 Reviewer와 실행 Reviewer를 각각 추가: 독립성은 더 강하지만 작은 Spring 테스트 요청에도
  에이전트와 handoff가 과도하게 늘어난다. 기존 Quality Reviewer가 독립 요구사항 대조와 실행 검증을
  함께 맡는 것으로 충분하다.

## 가정·트레이드오프

- 별도 Agent 실행으로 시간과 토큰 사용량이 증가한다.
- 서로 다른 Agent도 같은 모델 계열의 편향을 공유할 수 있으므로 역할 분리만으로 절대적 객관성을
  보장하지 않는다. 원 요청 추적표, 실제 테스트 실행과 결함 주입 결과를 외부 신호로 함께 사용한다.
- Reviewer에게 생성자의 대화가 아니라 파일 산출물만 전달해 anchoring을 줄인다.
- 각 역할이 앞선 대화 맥락을 다시 추론해야 해 실행 비용은 늘지만, 이름만 다른 동일 컨텍스트의
  형식적 역할 분리를 방지한다.
- 이미 끝난 실행의 Builder 식별자가 기록되지 않았다면 소급해 추정하지 않는다. 새 Builder 실행이
  현재 구현을 재확인하고 자기 식별자를 남긴 뒤 새 Reviewer가 세 주체를 검증한다.

## 재검토 조건

- 10회 이상의 실제 실행에서 별도 Designer가 찾거나 예방한 결함이 없고 비용만 증가한다.
- Quality Reviewer의 의미 검증과 실행 검증 책임이 커져 한쪽을 반복적으로 누락한다.
- 실행 플랫폼이 독립 컨텍스트 또는 서로 다른 실행 주체를 제공하지 않는다.
