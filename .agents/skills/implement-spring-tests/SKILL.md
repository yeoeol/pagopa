# Implement Spring Tests

## 진입 조건

- `artifacts/02-test-cases.md`가 존재한다.
- 승인 상태가 명시되어 있고 대화에서 사용자가 같은 범위를 승인했다.
- 승인 후 대상 코드나 관련 사용자 변경이 달라지지 않았다.

하나라도 만족하지 않으면 코드를 수정하지 않고 Orchestrator에 되돌린다.

## A 방식 절차

1. 승인된 케이스와 수정 파일을 다시 확인한다.
2. 가장 가까운 기존 테스트의 framework, assertion, mock, fixture와 명명 스타일을 따른다.
3. 한 테스트가 한 가지 행동과 결과를 읽기 쉽게 드러내도록 구성한다.
4. Given/When/Then 또는 Arrange/Act/Assert의 논리적 구획을 유지하되, 기존 파일에 없는 장식용
   주석을 일괄 추가하지 않는다.
5. 반복 제거가 가독성을 실제로 높일 때만 대상 테스트 클래스 내부에 private helper를 만든다.
6. 승인된 정상·예외·경계값·회귀 케이스만 구현한다.
7. 변경 파일과 구현 결정을 `artifacts/03-implementation.md`에 저장한다.

## 동시성 테스트 추가 규칙

- 실행을 동시에 시작시키는 명시적 gate를 사용하고 임의의 `Thread.sleep`에 기대지 않는다.
- 완료 여부에 제한 시간을 두고 그 결과를 반드시 assertion한다.
- 성공, 예상된 실패와 예상하지 못한 실패의 합계가 전체 작업 수와 일치해야 한다.
- 예상된 예외도 오류 코드까지 분류하고 삼키지 않는다.
- executor와 기타 자원은 실패 경로에서도 정리한다.
- 참여자 수와 thread 수는 검증 목적에 필요한 최소값으로 두고, 큰 부하 측정과 정확성 테스트를
  한 테스트에 섞지 않는다.

## 금지 행동

- 운영 코드와 `build.gradle`을 변경하지 않는다.
- 공용 Fixture, 공용 concurrency runner 또는 다른 테스트 파일로 리팩터링하지 않는다.
- 테스트를 통과시키려고 assertion을 삭제·완화하거나 예외를 무시하지 않는다.
- 승인되지 않은 추가 케이스를 끼워 넣지 않는다.
- `git add`, `git commit`, `git push`를 실행하지 않는다.

운영 코드 결함이나 의존성 부족으로 구현할 수 없으면 변경을 확대하지 말고 증거와 선택지를
Orchestrator에 반환한다.

## 완료 체크

- 모든 변경 줄이 승인된 테스트 케이스에 연결되는가?
- 테스트 이름만으로 조건과 기대 결과를 이해할 수 있는가?
- setup과 helper가 테스트의 핵심 행동을 숨기지 않는가?
- 사용자 변경을 덮어쓰지 않았는가?
