# Design Spring Test Cases

## 목적

테스트 코드보다 먼저 왜 필요한 테스트인지 합의할 수 있는 목록을 만든다.

이 Skill은 `spring-test-case-designer`가 `fork_turns="none"` 또는 동등한 무상속 방식으로 생성된
새 세션에서 사용한다. 다른 역할의 대화·메모리를 전달받지 않으며, 같은 실행 주체가
`verify-spring-tests`로 자기 설계를 최종 검증하지 않는다.

## 절차

1. `artifacts/00-request.md`, `artifacts/01-project-context.md`와 대상 코드를 읽고 작성 역할,
   canonical task name 또는 실행 ID, 세션 격리 방식과 허용된 입력을 기록한다.
2. 보호할 동작과 실패했을 때의 영향을 한 문장으로 정의한다.
3. 다음 유형을 각각 검토한다.
   - 정상: 대표적인 성공 흐름과 최종 상태
   - 예외: 명시된 계약 위반과 예외 타입·오류 코드·부수 효과 없음
   - 경계값: 최소·최대·0·빈 값·구간 끝 등 실제 계약 경계
   - 회귀: 과거 결함 또는 변경으로 깨질 가능성이 높은 불변식
4. 의미 없는 유형은 억지로 채우지 말고 `해당 없음`의 근거와 대체 검증을 적는다.
5. 각 케이스에 테스트 수준, 준비 비용, 격리 범위, 예상 assertion과 회귀 위험을 적는다.
6. 동시성 테스트라면 참여자 수, 공유 자원, 시작 게이트, 완료 제한 시간과 cleanup을 추가하고
   다음 판정 계약을 분리해 적는다.
   - `성공 수 + 승인된 예상 실패 수 = 전체 작업 수`
   - 예상하지 못한 실패 수는 별도로 `0`인지 검증한다.
   - 승인된 예상 실패는 예외 타입과 오류 코드별 예상 개수까지 검증한다.
   - 예상하지 못한 실패가 생기면 타입·오류 코드·메시지를 실패 근거로 남긴다.
   - 최종 DB 불변식은 작업 결과 집계와 별도로 검증한다.
7. 사용자 요구사항 → 시나리오 ID → 예상 assertion의 양방향 추적표를 만든다.
8. A 방식에서 수정할 정확한 테스트 파일을 정하고 `artifacts/02-test-cases.md`에 저장한다.
9. 승인 상태를 `사람 승인 필요`로 두고 Orchestrator에 반환한다.

재설계에서는 기존 구현과 검증 결과를 읽기 전에 원 요청과 운영 코드만으로 1차 요구사항·assertion
목록을 확정한다. 기존 목록과의 비교는 그 뒤에 수행해 구현 결과에 맞춰 시나리오를 역으로 만드는
편향을 막는다.

| --- | --- | --- | --- | --- | --- | --- | --- | --- |

각 행 아래에는 필요한 경우 공식 근거, 제외한 대안과 준비 비용을 짧게 적는다.

## 품질 기준

- 테스트 이름만 바꾼 중복 케이스를 만들지 않는다.
- 구현 세부사항보다 외부에서 관찰 가능한 결과를 검증한다.
- exception 클래스만이 아니라 의미 있는 오류 코드와 부수 효과도 검토한다.
- 경계값은 도메인 계약이나 실제 조건문에서 도출한다.
- 회귀 테스트는 어떤 결함을 막는지 설명할 수 있어야 한다.
- 동시성 테스트는 전체 작업 수 합계만으로 성공을 판정하지 않는다.
- 모든 사용자 요구사항이 하나 이상의 시나리오와 assertion에 연결되고, 모든 시나리오도 원
  요구사항 또는 코드 위험으로 역추적되어야 한다.
- 작성 역할과 실행 주체가 없으면 승인 가능한 테스트 목록으로 표시하지 않는다.
- 다른 역할의 대화·메모리를 상속하지 않은 세션 격리 증거가 없으면 승인 가능한 목록으로 표시하지
  않는다.
- 코드와 빌드 파일을 수정하지 않는다.
