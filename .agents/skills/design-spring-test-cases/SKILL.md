# Design Spring Test Cases

## 목적

테스트 코드보다 먼저 왜 필요한 테스트인지 합의할 수 있는 목록을 만든다.

## 절차

1. `artifacts/00-request.md`, `artifacts/01-project-context.md`와 대상 코드를 읽는다.
2. 보호할 동작과 실패했을 때의 영향을 한 문장으로 정의한다.
3. 다음 유형을 각각 검토한다.
   - 정상: 대표적인 성공 흐름과 최종 상태
   - 예외: 명시된 계약 위반과 예외 타입·오류 코드·부수 효과 없음
   - 경계값: 최소·최대·0·빈 값·구간 끝 등 실제 계약 경계
   - 회귀: 과거 결함 또는 변경으로 깨질 가능성이 높은 불변식
4. 의미 없는 유형은 억지로 채우지 말고 `해당 없음`의 근거와 대체 검증을 적는다.
5. 각 케이스에 테스트 수준, 준비 비용, 격리 범위, 예상 assertion과 회귀 위험을 적는다.
6. 동시성 테스트라면 참여자 수, 공유 자원, 시작 게이트, 완료 제한 시간, 성공·실패 합계,
   최종 불변식과 cleanup을 추가한다.
7. A 방식에서 수정할 정확한 테스트 파일을 정하고 `artifacts/02-test-cases.md`에 저장한다.
8. 승인 상태를 `사람 승인 필요`로 두고 Orchestrator에 반환한다.

각 행 아래에는 필요한 경우 공식 근거, 제외한 대안과 준비 비용을 짧게 적는다.

## 품질 기준

- 테스트 이름만 바꾼 중복 케이스를 만들지 않는다.
- 구현 세부사항보다 외부에서 관찰 가능한 결과를 검증한다.
- exception 클래스만이 아니라 의미 있는 오류 코드와 부수 효과도 검토한다.
- 경계값은 도메인 계약이나 실제 조건문에서 도출한다.
- 회귀 테스트는 어떤 결함을 막는지 설명할 수 있어야 한다.
- 코드와 빌드 파일을 수정하지 않는다.
